# 06. Worktree в OpenCode V2: параллельные сессии в отдельных рабочих копиях

Два агента в одном каталоге — это два штатника за одним компьютером: оба дёргают одни файлы, оба держат индекс, оба хотят свою ветку. Пока агент A рефакторит `main`, агент B уже закоммитил поверх. Решение V2 знакомо любому git-пользователю: **у каждой сессии — своя рабочая копия репозитория** (worktree); управление копиями собрано в три инструмента, а ключевой сценарий «создал копию — перенёс в неё сессию» — это два вызова: `worktree_create` + `session_move`. Под катом — фундамент из git, инструменты V2, размещение, стратегии и сценарии параллельных агентов. Источник фактов по инструментам — [V2 tools docs](https://opencode.ai/v2/docs/tools).

```text
БЕЗ WORKTREE: оба агента топчутся в одном каталоге

     агент A ──>  ./repo  <── агент B
              (main, одни файлы, один индекс)

С WORKTREE: у каждой сессии своя рабочая копия

     агент A ──>  ./repo                (main)
     агент B ──>  …/worktree/login      (login)
```

## Мини-глоссарий

- **worktree** — связанная рабочая копия репозитория: отдельный каталог со своей извлечённой веткой при общем объектном сторе.
- **canonical checkout** — основной каталог репозитория (первичный клон); от него отсчитываются относительные пути.
- **стратегия worktree** — способ создания рабочей копии: git — встроенный дефолт, плагин может зарегистрировать собственную.
- **`session_move`** — инструмент неймспейса `opencode`: перенос сессии в другой каталог.
- **project-ID** — идентификатор проекта; первые 6 его символов становятся именем подпапки для worktree по умолчанию.

## Фундамент: git worktree

Всё, что V2 предлагает под именем worktree, стоит на [git worktree](https://git-scm.com/docs/git-worktree): репозиторий может извлечь **несколько веток одновременно в разные каталоги**, а хранить коммиты и файлы — один раз, в общем объектном сторе. Ветки — лишь указатели; рабочие копии — окна в них:

```text
        ОДИН РЕПОЗИТОРИЙ: общий объектный стор
        (коммиты и файлы хранятся один раз)
             main *       login       refactor/auth
                |            |              |
                v            v              v
           +---------+  +---------+    +---------+
           | каталог |  | каталог |    | каталог |
           |  (main) |  | (login) |    | (refact)|
           +---------+  +---------+    +---------+
                |            |              |
           сессия A      сессия B       сессия C
           (агент)       (агент)        (агент)
```

Ограничения самого git-worktree (концептуально, по [git-worktree docs](https://git-scm.com/docs/git-worktree)): одна ветка не может быть извлечена в двух worktree одновременно — параллельные сессии должны расходиться по веткам. И пара правил о ручных операциях с каталогом: после ручного **удаления** git рано или поздно зачистит админ-данные сам (через gc) — `prune` делает это немедленно; после ручного **переноса** копию переподключают через `repair`.

## Три инструмента V2

Инструменты `worktree_create` / `worktree_list` / `worktree_remove` живут в Code Mode-неймспейсе `opencode` — о самом Code Mode расскажет [заметка 07](07_opencode-codemode.md) цикла. Сценарий из доков показывает задумку одним жестом: «Create a worktree named "login" and move this session into it» — создаётся именованная рабочая копия, и сессия переезжает в неё (`session_move`): текущий агент продолжает работу уже в отдельном каталоге, не мешая соседям.

| Инструмент | Что делает | Права |
|---|---|---|
| `worktree_create` | создаёт рабочую копию | встроенного permission-действия не запрашивает |
| `worktree_list` | показывает список рабочих копий | не запрашивает |
| `worktree_remove` | удаляет рабочую копию | требует права `edit` на каталог worktree; параметр `force` — отбросить незакоммиченные изменения |

Асимметрия прав логична: создание и смотр безобидны, а удаление каталога — это потеря возможной работы, поэтому оно под правом `edit` (механика permissions — из [заметки 04](04_opencode-multiagent.md); работу инструментов, как и любых других, можно аудировать tool-хуками из [заметки 05](05_opencode-commands-hooks.md)).

## Где живут worktree

Размещение задаёт настройка `worktree.directory` ([V2 config docs](https://opencode.ai/v2/docs/config)):

- относительный путь считается от **canonical checkout** — основного каталога репозитория;
- без настройки — data-каталог сервера, в подпапку `worktree/<первые 6 символов project-ID>`; каждый созданный worktree записывается в inventory проекта (с recorded owner/strategy), так что точная формула такая: копии создаются в data-каталоге сервера и учитываются на уровне проекта — а если упрощать до «живут на стороне сервера, не клиента», это именно упрощение (архитектурный фон — [заметка 03](03_opencode-architecture-config.md));
- важно: **смена настройки не перемещает уже созданные worktree** — старые копии остаются там, где родились.

## Стратегии

Способ создания рабочей копии — не зашит намертво:

- **git** — встроенная стратегия и дефолт;
- **плагин** может зарегистрировать собственную стратегию worktree — и автоматически становится дефолтом в своём рантайме ([server plugin docs](https://opencode.ai/v2/docs/build/plugins/server)). В доках в этой связи упомянута нативная snapshot-операция **Rift** — это свойство конкретной реализации (у операции нет опции выбора ref); сами же стратегии, по докам, управляют локальными каталогами.

## Сценарии: параллельные агенты

Главный сайт OpenCode продаёт это прямо: «Multi-session: start multiple agents in parallel…» ([opencode.ai](https://opencode.ai/)). Идея: сколько задач — столько сессий, каждая — в своём worktree со своей веткой; никто ни на кого не наступает. Что это устоявшийся паттерн для AI-агентов вообще (не только OpenCode) — подтверждает **вторичный источник**: [git worktrees for parallel AI coding agents (upsun)](https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents).

Как worktree встаёт в картину цикла и git-материалов:

- **субагенты vs worktree** — две ортогональные оси. Субагенты ([заметка 04](04_opencode-multiagent.md)) — делегирование *внутри* одной сессии: оркестратор раздаёт брифы исполнителям. Worktree — параллельность *между* сессиями: два независимых окна в репозиторий. Комбинация законна: оркестратор в одной копии, вторая копия — для смежной задачи.
- **зачем вообще несколько живых веток** — вопрос моделей ветвления: [01. Модели ветвления](../../materials/01_tbd-branching-models.md) разбирает, сколько веток должно жить одновременно и как часто их сливать (TBD против Git Flow/GitHub Flow) — worktree просто даёт каждой параллельной сессии физическое место под её ветку.
- **чем сливать ветку worktree обратно** — [08. rebase vs merge](../../materials/08_git-rebase-merge.md): merge пришивает работу как есть, rebase пересоздаёт поверх нового основания; ветка из рабочей копии в итоге возвращается в main одним из этих способов.

|---|---|
| Что это | параллельные сессии в связанных рабочих копиях одного репозитория (git worktree) |
| Инструменты | `worktree_create` / `worktree_list` / `worktree_remove` в неймспейсе `opencode` (Code Mode — заметка 07) |
| Ключевой сценарий | «Create a worktree named "login" and move this session into it» + `session_move` |

# 02. OpenCode v1 vs V2: что изменилось и как мигрировать

Главная перемена OpenCode V2 — не новые кнопки, а смена скелета: то, что в V1 было приложением «всё-в-одном», стало тонким клиентом перед общим фоновым сервером. Отсюда и главная новость для миграции: осознанно сломано ровно **три** вещи — plugin API, server API и конфиг терминального клиента; всё остальное задумано совместимым с V1, и если что-то работает иначе — это compatibility bug, а не «новая философия». Заметка для тех, кто уже знает OpenCode v1 или другие AI-агенты (Claude Code, Codex CLI): азы не разбираем, фокус — отличия V2 и путь переезда. Источник фактов — официальный гайд [Migrate from V1 (OpenCode V2 docs)](https://opencode.ai/v2/docs/migrate-v1); вторичные источники помечены явно.

Это первая заметка цикла об OpenCode V2 и одновременно мост от предыдущей: [Как читать архитектуру LLM-моделей](../01_how-to-read-llm-architecture.md) — про то, что происходит *внутри* модели, а этот цикл — про harness («упряжь») *вокруг* неё: агентов, инструменты, сессии, права.

## Мини-глоссарий

- **background service (shared background server)** — единый фоновый сервер на учётную запись: OpenCode находит уже запущенный или стартует его сам; именно серверу принадлежат сессии, конфигурация, интеграции, permissions и исполнение инструментов.
- **breaking change** — намеренно несовместимое изменение; в V2 их ровно три, весь остальной список «что поменялось» — это переименования и автоматические трансляции.
- **compatibility bug** — несовместимость там, где совместимость задумана: чинится как обычный баг и не требует действий при миграции.
- **native V2 config** — конфиг, целиком записанный в полях формата V2; противоположность — V1-конфиг, который V2 умеет читать и нормализовать в памяти, не переписывая файл.
- **primary-агент** — полноценный агент верхнего уровня; в такие превращаются записи старой карты `mode` из V1.
- **model variant** — «приклеенный» к имени модели через `#` суффикс с настройками; с V2 именно здесь живут параметры генерации вроде `temperature`.
- **dual-support плагин** — один пакет, который экспортирует сразу и V1-функцию `server()`, и V2-функцию `setup()` — работает в обоих мирах.

## Центральный сдвиг: от «приложения-всё-в-одном» к общему фоновому серверу

В V1 каждый запуск — сам себе хозяин: свой сервер, свои сессии, свой конфиг, свои интеграции. В V2 [one shared background server per account](https://opencode.ai/v2/docs/cli), а локальные клиенты — TUI, desktop, web через `opencode pair` — становятся тонкими и подключаются к нему:

```text
V1: каждый запуск — замкнутый мир

    терминал 1              терминал 2             desktop
 +---------------+      +---------------+      +---------------+
 |   opencode    |      |   opencode    |      |   opencode    |
 |  свой сервер  |      |  свой сервер  |      |  свой сервер  |
 |  свои сессии  |      |  свои сессии  |      |  свои сессии  |
 |  свой конфиг  |      |  свой конфиг  |      |  свой конфиг  |
 |  интеграции   |      |  интеграции   |      |  интеграции   |
 +---------------+      +---------------+      +---------------+
        параллельные миры: сессии и права друг о друге не знают

V2: тонкие клиенты вокруг одного сервера на учётную запись

   TUI 1         TUI 2         desktop       web (opencode pair)
     |             |              |                   |
     +-------------+--------------+-------------------+
                              |
                              v
        +------------------------------------------+
        |         SHARED BACKGROUND SERVICE        |
        |     сессии · конфигурация · интеграции   |
        |  permissions · исполнение инструментов    |
        +------------------------------------------+
```

Практический смысл схемы: сессия, начатая в одном клиенте, живёт на сервере — общий «мозг» на всех клиентов. Режимы запуска позволяют и отступить от схемы: `--standalone` поднимает приватный сервер, `--server <URL>` подключает клиент к конкретному серверу, а `opencode service set disabled true` вовсе отключает shared-сервис.

Важное следствие для переезда: обе версии используют одну и ту же команду `opencode` и **side-by-side не ставятся** — curl-инсталлятор V2 просто заменяет бинарник V1; V1, поставленный через пакетный менеджер, придётся удалить.

## Ровно три breaking changes — и всё остальное «должно работать»

| № | Что сломали намеренно | Как было в V1 | Как стало в V2 |
|---|----------------------|---------------|----------------|
| 1 | Plugin API | старый API плагинов | новый plugin API; V1-плагины не запускаются |
| 2 | Server API | старые контракты | новые контракты + новый клиентский SDK `@opencode/client` |
| 3 | Конфиг терминального клиента | слоёные `tui.json(c)` | один глобальный `~/.config/opencode/cli.json`; авто-мигрируют при первом старте только глобальные настройки `tui.json` и preferences — проектные клиентские конфиги не мигрируются, ведь клиентский конфиг в V2 глобальный |

Все три — прямые следствия нового скелета: сервер владеет интеграциями и исполнением инструментов (плагины и server API переехали в его мир), а TUI стал просто одним из клиентов (поэтому его личный конфиг сжался до одного файла).

Всё, что не попало в таблицу, задумано совместимым. Конкретно про конфиги: V1 и V2 читают их **из одних и тех же мест** — существующие файлы работают без конвертации, V2 нормализует V1-поля в памяти и не переписывает файл на диске. Не изменились и ключевые поля верхнего уровня: `shell`, `model`, `default_agent`, `watcher`, `formatter`, `instructions`, `enterprise`, `tool_output`; Markdown-команды и скиллы; те же системные/глобальные/проектные локации конфигов.

Мой вывод-рамка для чтения всего дальнейшего: **если после апгрейда что-то ведёт себя не как в V1 — сначала проверьте, не compatibility bug ли это, и только потом ищите в списке переименований.**

## Карта переименований: до / после

Формат V1 в конфиге не запрещён — он депрекирован и транслируется на лету. Но чтобы читать чужие V2-конфиги и осознанно решать, конвертироваться или нет, полезна карта соответствий:

| Область | V1 | V2 |
|---|---|---|
| Раздел агентов | `agent` | `agents` |
| Системный промпт агента | `prompt` | `system` |
| Выключение агента | `disable` | `disabled` |
| Лимит шагов агента | `maxSteps` | `steps` |
| Вариант модели | отдельное поле `variant` | суффикс модели через `#` (model variant) |
| Карта режимов | `mode` | записи становятся primary-агентами |
| Команды | `command` | `commands` |
| Субзадачи в командах | `subtask` | `subagent` (легаси-имя принимается) |
| Провайдеры | `provider` | `providers` |
| Пакет провайдера | `npm` | `package` с префиксом `aisdk:` |
| Базовый URL | `api` | `settings.baseURL` |
| Опции провайдера | `options` | делится на `settings` / `headers` / `body` |
| ID провайдеров | `azure-cognitive-services`, `google-vertex-anthropic` | консолидированы: `azure`, `google-vertex` |
| MCP: где список серверов | — | под ключом `mcp.servers` |
| MCP: включённость | `enabled` | инверсный `disabled` |
| MCP: таймауты | `timeout` | делится на `catalog` / `execution` |
| MCP: OAuth-поля | — | записываются в snake_case |
| Compaction | `preserve_recent_tokens`, `reserved` | `keep.tokens`, `buffer` |
| Compaction: устаревшее | `tail_turns`, `prune` | игнорируются с warning |
| Skills | `skills.paths` + `skills.urls` | один массив `skills` |
| Плагины | `plugin`, кортеж «пакет + опции», локальные файлы | `plugins`, объект `{package, options}`, локальные пути — только каталоги |
| Автообновление | `autoupdate`: `false` / `"notify"` / `true` | `update`: `"disable"` / `"notify"` / `"auto"` |
| «Малая модель» | `small_model` | `agents.title.model` |
| Вкл/выкл провайдеров | `enabled_providers` / `disabled_providers` | [policies](https://opencode.ai/v2/docs/policies) |
| Глубина субагентов | top-level `subagent_depth` | `experimental.subagent_depth` |

Карта выборочная — собраны самые ходовые ключи; полная таблица соответствий (включая `snapshot`→`snapshots`, `attachment`→`media`, `reference`→`references` и модельные поля) — в [migrate-v1 guide](https://opencode.ai/v2/docs/migrate-v1).

### Permissions: от словаря к списку правил

Самая концептуальная смена формата. V1 группировал разрешения по инструментам — словарь с паттернами команд. V2 — один упорядоченный массив записей `{action, resource, effect}`, где **побеждает последнее совпавшее правило** — мышление как у ACL/firewall, а не у «папок по инструментам» (формат: [V2 permissions docs](https://opencode.ai/v2/docs/permissions)). Переименовались и действия: `bash`→`shell`, `task`→`subagent`, `write`/`patch`→`edit`.

### Агентные файлы: четыре каталога и один формат

V2 обнаруживает все четыре каталога — `agent/`, `agents/`, `mode/`, `modes/`; предпочтительное место — `.opencode/agents/<name>.md` (детали: [V2 agents docs](https://opencode.ai/v2/docs/agents)). Файлы из `mode/` читаются как primary-агенты. V1-frontmatter депрекирован, но автотранслируется. Правило чтения файла: он интерпретируется целиком в одном формате — появились V2-поля, значит, читается как V2.

### Правило смешения форматов

Переезжать можно поэтапно: внутри `mcp`, `compaction`, `experimental` V1- и V2-поля могут соседствовать. А вот внутри отдельного agent / provider / command / model формат не выводится рекурсивно: конфликтующие V1/V2 значения в одном объекте дают warnings, при этом остальные валидные настройки продолжают загружаться.

## Грабли миграции: где V1-интуиция подводит

| Грабля | Что происходит в V2 | Как вернуть ожидаемое |
|---|---|---|
| Пути вне проекта | **Грабля безопасности**: `external_directory` разрешён по умолчанию, тогда как V1 спрашивал разрешение | правило с action `external_directory` и effect `ask` |
| V1-плагины | не запускаются; переноса файла недостаточно (в доках — явный warning) | переписать на новый API; для обоих миров — dual-support: один default export с V1 `server()` и V2 `setup()` |
| Инструкции | V2 обнаруживает только `AGENTS.md` — глобальный `~/.config/opencode/AGENTS.md` плюс поиск от текущего каталога вверх до home/корня проекта ([V2 instructions docs](https://opencode.ai/v2/docs/instructions)) | если V1-сетап полагался на фолбэк `CLAUDE.md` — перенести содержимое в `AGENTS.md` |
| `lsp` | поле принимается, но V2 не запускает language servers | заменить на lint / typecheck / compiler |
| todos | выключены по умолчанию | `experimental.todo: true` |
| Файлы из `mode/` | автоматически становятся primary-агентами | при переносе в `agents/` добавить `mode: primary` |
| Server auth | `OPENCODE_SERVER_USERNAME` удалён: username теперь всегда `opencode` | пароль — `OPENCODE_PASSWORD` (старое `OPENCODE_SERVER_PASSWORD` тоже работает) |
| `request.body` агента | поле сохраняется, но модели не отправляется: `temperature` / `top_p` через него больше не работают | задавать на model variant — суффикс `#` у модели |
| «Молчаливые» поля | `logLevel`, `server`, top-level `subagent_depth`, V1 `batch_tool`, `openTelemetry`, `primary_tools`, `continue_loop_on_deny`, часть полей provider/model — принимаются, но не работают | свериться с гайдом миграции и вычистить |
| Сетап на OMO | набор агентов OMO ([oh-my-openagent, code-yeongyu](https://github.com/code-yeongyu/oh-my-openagent)) монтируется через plugin API v1 — в V2 не запускается | не нужен: нативные агенты V2 — тема заметки 04 цикла (подробнее ниже) |

### Куда делся OMO

OMO — Oh My OpenAgent, ранее Oh My OpenCode, — сторонний open-source набор готовых агентов, субагентов и режимов работы для OpenCode v1; устанавливался поверх opencode как пакет — пользователи нередко просто просили агента «установи OMO». Своих субагентов OMO регистрировал через plugin API v1 (issue #5701 проекта прямо это фиксирует) — а V1-плагины в V2 не запускаются, это breaking change №1 (plugin API). Но потеря невелика: в V2 мультиагентная конфигурация нативная — поле `agents`, markdown-файлы агентов, механизм Selection, субагенты. Функция, ради которой ставили OMO, встроена в сам OpenCode — OMO в V2 не нужен. Как заменить личный OMO-сетап нативными агентами V2 — тема [заметки 04](04_opencode-multiagent.md) цикла про мультиагентное конфигурирование.

## Путь миграции: пять шагов как концепт

Официальный сценарий — не «снеси и поставь заново», а постепенный переезд с параллельной валидацией:

```text
   (1) КОНФИГИ — КАК ЕСТЬ
   ничего не конвертируем: V1 и V2 читают одни и те же файлы,
   V2 нормализует V1-поля в памяти, не переписывая файл
        |
        v
   (2) СТАРТ V2 + ПРОВЕРКА
   модели · креды · агенты · permissions · MCP
        |
        v
   (3) ПЛАГИНЫ
   переписывание на новый API — копирования файла мало
        |
        v
   (4) SERVER-API-ИНТЕГРАЦИИ
   новые контракты; клиентский SDK @opencode/client
        |
        v
   (5) NATIVE V2-КОНФИГ (опционально)
   конвертация по желанию и поэтапно: V1- и V2-поля могут
   сосуществовать на верхнем уровне

   сбоку весь путь сопровождает копия V1-сетапа (пока идёт валидация)
   и запрет: V1 не направляем на файлы, сконвертированные в native V2
```

Самое неочевидное в шаге 5: конвертацию можно **попросить на естественном языке** («Migrate my OpenCode configuration…») — и она опциональна. V1-формат не «выключат», он транслируется, так что спешить некуда. Единственное жёсткое правило — не смешивать миры: V1, смотрящий на native-V2-файлы, — сценарий без поддержки.

## Резюме: чек-лист переезда

1. Помните рамку: сломаны ровно три вещи — plugin API, server API, `cli.json`. Всё остальное, что ведёт себя иначе, — кандидат в compatibility bug.
2. Конфиги не трогаем, пока V2 не проверен: он читает те же файлы и не переписывает их на диске.
3. После старта V2 проверяем пять зон: модели, креды, агенты, permissions, MCP.
4. Безопасность: если V1 спрашивал разрешение на пути вне проекта — в V2 верните это правилом `external_directory` с effect `ask`.
5. Инструкции: `CLAUDE.md` больше не подхватывается — только `AGENTS.md`.
6. `lsp` не заработает — планируйте замену на lint/typecheck/compiler.
7. Плагины переносятся переписыванием; нужен оба мира — делайте dual-support export.
8. Username сервера теперь всегда `opencode`; пароль — `OPENCODE_PASSWORD`.
9. До конца валидации держим копию V1-сетапа и не направляем V1 на native-V2-файлы.

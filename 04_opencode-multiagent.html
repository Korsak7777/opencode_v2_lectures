04. Мультиагенты в OpenCode V2: primary, субагенты, Selection и конец эры OMO

Один универсальный агент — как швейцарский нож: всё при нём, но ни для чего не идеален. Мультиагентность закрывает три потребности разом: специализацию (каждый профиль заточен под свою роль), права (у каждого агента свои permissions) и разделение труда (оркестратор думает, исполнители делают). В V2 агенты — first-class сущности: свой markdown-файл, своя модель, свои права, без сторонних прослоек. Заметка 02 цикла обещала: «как заменить личный OMO-сетап нативными агентами V2 — тема заметки 04». Обещание выполняется. Источник фактов — V2 agents docs.

· Мини-глоссарий

primary-агент
главный агент сессии: именно с ним идёт диалог; задаётся полем mode: primary.
субагент (subagent)
агент, который не стартует сам, а запускается другим агентом через tool subagent.
Selection
механизм выбора агентов: стартовый определяется настройкой default_agent, субагентов выбирает primary-агент по полю description.
description
«витрина» агента: текст, который видит выбирающая модель; от него зависит, позовут агента или нет.
last-match-wins
семантика списка permissions: побеждает последнее совпавшее правило.
оркестратор-исполнители
паттерн: primary-агент, которому запрещено всё, кроме запуска конкретных субагентов.

· Агент = именованный профиль

Агент — это не «чат с ролью», а именованный профиль из четырёх слагаемых:

агент = system-промпт + модель + permissions + отображениезадаётся файлом .opencode/agents/<name>.md или полем agents в JSONC-конфиге
  • markdown-файл .opencode/agents/<name>.md: тело файла — system-промпт, frontmatter — поля конфигурации (концепция проектного слоя .opencode/ — из заметки 03);
  • поле agents в JSONC-конфиге.

Вложенные пути дают вложенные ID: файл в подкаталоге становится агентом team/reviewer. Основные поля профиля:

ПолеСмысл
modeроль в сессии: primary / subagent / all (см. ниже)
description«витрина» для Selection — по ней выбирают субагента
modelмодель агента; наследуется от родителя, если не задана
permissionsсобственные правила агента
stepsлимит шагов
hidden / disabled / colorскрыть / выключить / подсветить агента
requestсохраняется, но модели пока не отправляется — в доках об этом warning

· Три режима: primary, subagent, all

primary
главный агент сессии; режим по умолчанию для новых кастомных агентов
subagent
запуск только через tool subagent, самостоятельно не стартует
all
работает в обеих ролях

Механизм выбора агентов — двухуровневый, и на каждом уровне выбирает разное:

Стартового агента назначает человек — настройкой default_agent. Субагентов назначает машина: OpenCode показывает description модели, выбирающей, какого агента запустить. Отсюда практический вывод:

description — не комментарий, а интерфейс выбора; расплывчатое описание — субагента просто не позовут. Если default_agent не существует, скрыт или не primary-совместим — срабатывает fallback: сначала встроенный build, затем первый видимый primary.

Как это работает
Выберите формулировку задачи наверху. Primary-агент получит её, прочитает витрины (description всех агентов), подсветит совпадения — и луч выбора остановится на подходящем агенте. Здесь появится объяснение выбора.

Формулировки задач — иллюстративные; тексты витрин взяты из заметки: описания встроенных агентов (build, plan, general, explore) — из таблицы встроенных, роли material-* — из живого кейса ниже. description — интерфейс выбора: модель primary читает витрины.

· Permissions мультиагента: родитель решает, ребёнок отвечает

Права в мультиагентной системе работают в два этажа:

Два этажа прав
родитель (parent)решает, кого можно запускать: правила с action subagent в его permissions
запущенный ребёнок (subagent)живёт по собственным permissions — они и только они определяют, что ему можно
  • Действия: shell, edit, subagent, read/glob/grep, webfetch/websearch, skill.
  • Эффекты: allow / ask / deny.
  • Побеждает последнее совпавшее правило — last-match-wins (V2 permissions docs).
  • Слияние слоёв: глобальные permissions применяются до агентских, агентские правила уточняют их.

Из этого вырастает готовый паттерн из доков — «оркестратор»: deny subagent *, затем allow для конкретных ID агентов. Last-match-wins превращает пару правил в белый список исполнителей.

Интерактив 2 · last-match-wins

Конструктор оркестратора: permissions и белый список исполнителей

Слева — permissions оркестатора newton из живого кейса: deny edit/shell/subagent *, затем allow десяти material-*. Меняйте эффект правила (allow/ask/deny), порядок (↑/↓), включайте/отключайте правила, добавляйте свои — панель «Кого оркестратор сможет запустить» справа пересчитывается на лету. Клик по карточке исполнителя подсвечивает в списке правил пару «последнее совпавшее побеждает»: стрелка «◄ last-match-wins» встанет у победившей строки, перекрытые строки будут зачёркнуты.

исходный сетап: deny edit/shell/subagent * + allow десяти material-*
permissions агента newton · список сверху вниз
+ правило (в конец — последнее слово):
кого оркестратор сможет запустить · action subagent · кликните карточку
build · plan — mode: primary: главные агенты сессии, не исполнители — через tool subagent их не выбирают. В кейсе они доступны пользователю через переключатель (Tab).
Почему так?

Кликните карточку исполнителя — здесь появятся все совпавшие с его ID правила и отметка, какое из них победило (последнее совпавшее). Поменяйте порядок правил или их эффект — и победитель изменится на глазах.

Демонстрация семантики last-match-wins на правилах action subagent (кого запускать) и edit/shell (что может сам оркестратор). У запущенного субагента — собственные permissions, этот список он не наследует: например, material-researcher из кейса — read-only (deny edit/shell), даже если оркестратору позволено больше.

· Конец эры OMO: от чужих пресетов к своим агентам

Напоминание из заметки 02: OMO — Oh My OpenAgent (oh-my-openagent, code-yeongyu), ранее Oh My OpenCode, — сторонний набор готовых агентов и режимов для v1 (в его доках — explore, librarian, plan-consultant, plan-reviewer и другие). Ставился он в plugin-список конфига, а субагентов регистрировал через plugin API v1 (issue #5701) — тот самый breaking change №1: в V2 такие плагины не запускаются. Но главная новость не «сломалось», а «больше не нужно»: всё, что давал OMO, в V2 нативно.

Паттерн замены (практика, не цитата из доков): каждый «режим» OMO становится своим markdown-агентом в .opencode/agents/ — с продуманным description (по нему сработает Selection) и permissions по роли. Те же возможности, но файл лежит в вашем репозитории, читается глазами и ревьюится как код.

· Живой кейс: этот репозиторий

Эволюция на одном примере. В zettelkasten/AI_start.md — точка отсчёта: установка v1 тремя шагами, последний из которых «попросить opencode установить OMO». Сегодня тот же workflow выглядит так:

  • корневой opencode.jsonc задаёт default_agent: "newton" — и прямо в комментарии объясняет: механизм Selection, новые сессии стартуют с оркестратора, остальные агенты (build, plan) доступны через переключатель (Tab), а существующие сессии настройка не трогает;
  • в .opencode/agents/ — 11 агентов: оркестратор newton и десять исполнителей material-*.

newton — учебниковый «оркестратор-исполнители» из паттерна выше: mode: primary, модель glm-5.3, permissions «deny edit/shell/subagent *, затем allow десяти субагентам material-*» — сам оркестратор не редактирует файлы и не выполняет shell, вся работа делегирована. Исполнители специализированы по ролям — например, material-researcher: mode: subagent, лёгкая модель glm-5.3-flash (та самая, что разобрана в заметке 01), read-only права (deny edit/shell) — искать можно, менять нельзя:

# 04. Мультиагенты в OpenCode V2: primary, субагенты, Selection и конец эры OMO

Один универсальный агент — как швейцарский нож: всё при нём, но ни для чего не идеален. Мультиагентность закрывает три потребности разом: **специализацию** (каждый профиль заточен под свою роль), **права** (у каждого агента свои permissions) и **разделение труда** (оркестратор думает, исполнители делают). В V2 агенты — first-class сущности: свой markdown-файл, своя модель, свои права, без сторонних прослоек. Заметка [02 цикла](02_opencode-v1-vs-v2.md) обещала: «как заменить личный OMO-сетап нативными агентами V2 — тема заметки 04». Обещание выполняю. Источник фактов — [V2 agents docs](https://opencode.ai/v2/docs/agents).

## Мини-глоссарий

- **primary-агент** — главный агент сессии: именно с ним идёт диалог; задаётся полем `mode: primary`.
- **субагент (subagent)** — агент, который не стартует сам, а запускается другим агентом через tool `subagent`.
- **Selection** — механизм выбора агентов: стартовый определяется настройкой `default_agent`, субагентов выбирает primary-агент по полю `description`.
- **description** — «витрина» агента: текст, который видит выбирающая модель; от него зависит, позовут агента или нет.
- **last-match-wins** — семантика списка permissions: побеждает последнее совпавшее правило.
- **оркестратор-исполнители** — паттерн: primary-агент, которому запрещено всё, кроме запуска конкретных субагентов.

## Агент = именованный профиль

Агент — это не «чат с ролью», а именованный профиль из четырёх слагаемых: **system-промпт + модель + permissions + отображение**. Задать его можно двумя способами:

- **markdown-файл** `.opencode/agents/<name>.md`: тело файла — system-промпт, frontmatter — поля конфигурации (вспомните концепцию из [03 цикла](03_opencode-architecture-config.md): проектный слой `.opencode/`);
- **поле `agents`** в JSONC-конфиге.

Вложенные пути дают вложенные ID: файл в подкаталоге становится агентом `team/reviewer`. Основные поля профиля:

| Поле | Смысл |
|---|---|
| `mode` | роль в сессии: `primary` / `subagent` / `all` (см. ниже) |
| `description` | «витрина» для Selection — по ней выбирают субагента |
| `model` | модель агента; наследуется от родителя, если не задана |
| `permissions` | собственные правила агента |
| `steps` | лимит шагов |
| `hidden` / `disabled` / `color` | скрыть / выключить / подсветить агента |
| `request` | сохраняется, но модели пока не отправляется — в доках об этом warning |

## Три режима: primary, subagent, all

- **`primary`** — главный агент сессии; режим по умолчанию для новых кастомных агентов;
- **`subagent`** — запуск только через tool `subagent`, самостоятельно не стартует;
- **`all`** — работает в обеих ролях.

## Selection: кто кого выбирает

Механизм выбора агентов — двухуровневый, и на каждом уровне выбирает разное:

```text
   новая сессия стартует
          |
          v
   default_agent  (настройка из opencode.json - заметка 03)
          |
          |  агент существует, видим и primary-совместим?
          |  нет -> fallback: build, затем первый видимый primary
          v
   PRIMARY-АГЕНТ  (ведёт диалог с пользователем)
          |
          |  нужен помощник: tool `subagent`
          v
   выбор по description  («витрина» агента)
          |
          v
   СУБАГЕНТ  (живёт по собственным permissions)
```

Стартового агента назначает человек — настройкой `default_agent`. Субагентов назначает машина: OpenCode показывает `description` модели, выбирающей, какого агента запустить. Отсюда практический вывод: **description — не комментарий, а интерфейс выбора**; расплывчатое описание — субагента просто не позовут. Если `default_agent` не существует, скрыт или не primary-совместим — срабатывает fallback: сначала встроенный `build`, затем первый видимый primary.

## Встроенные агенты

| Агент | mode | Роль |
|---|---|---|
| `build` | primary | дефолтный главный агент |
| `plan` | primary | планирование без правки файлов |
| `general` | субагент | широкие права; сам субагентов запускать не может |
| `explore` | субагент | read-only поиск |
| `compaction` / `title` / `summary` | скрытые служебные | обслуживание сессии |

Раньше в этой таблице мог быть `scout` — в V2 встроенного `scout` нет.

## Permissions мультиагента: родитель решает, ребёнок отвечает

Права в мультиагентной системе работают в два этажа:

- **родитель (parent)** решает, *кого* можно запускать: правила с action `subagent` в его permissions;
- **запущенный ребёнок** живёт по *собственным* permissions — они и только они определяют, что ему можно.

Действия: `shell`, `edit`, `subagent`, `read`/`glob`/`grep`, `webfetch`/`websearch`, `skill`. Эффекты: `allow` / `ask` / `deny`. Побеждает последнее совпавшее правило — **last-match-wins** ([V2 permissions docs](https://opencode.ai/v2/docs/permissions)). Слияние слоёв: глобальные `permissions` применяются до агентских, агентские правила уточняют их.

Из этого вырастает готовый паттерн из доков — **«оркестратор»**: deny `subagent *`, затем allow для конкретных ID агентов. Last-match-wins превращает пару правил в белый список исполнителей.

## Конец эры OMO: от чужих пресетов к своим агентам

Напоминание из [заметки 02](02_opencode-v1-vs-v2.md): OMO — Oh My OpenAgent ([oh-my-openagent, code-yeongyu](https://github.com/code-yeongyu/oh-my-openagent)), ранее Oh My OpenCode, — сторонний набор готовых агентов и режимов для v1 (в его доках — explore, librarian, plan-consultant, plan-reviewer и другие). Ставился он в plugin-список конфига, а субагентов регистрировал через plugin API v1 ([issue #5701](https://github.com/code-yeongyu/oh-my-openagent/issues/5701)) — тот самый breaking change №1: в V2 такие плагины не запускаются. Но главная новость не «сломалось», а «больше не нужно»: всё, что давал OMO, в V2 нативно.

```text
БЫЛО: v1 + OMO - мультиагентность через сторонний плагин

     вы
     |
     v
   opencode v1 ---- plugin-список в конфиге
     |
     v
   [ПЛАГИН OMO]   <- чужие пресеты: explore, librarian,
     |                plan-consultant, plan-reviewer, ...
     v                (субагенты через plugin API v1)
   готовые режимы работы

СТАЛО: V2 - мультиагентность нативная, агенты first-class

     вы
     |
     v
   primary-агент   <- свой файл .opencode/agents/<name>.md
     |                (system-промпт + модель + permissions)
     |  tool `subagent`
     v
   субагенты       <- тоже свои файлы; выбираются по description,
                      живут по собственным permissions
```

Паттерн замены (практика, не цитата из доков): каждый «режим» OMO становится **своим** markdown-агентом в `.opencode/agents/` — с продуманным `description` (по нему сработает Selection) и permissions по роли. Идейно это переход от «чужих пресетов через плагин» к «своим агентам-first-class-сущностям»: те же возможности, но файл лежит в вашем репозитории, читается глазами и ревьюится как код.

### Живой кейс: этот репозиторий

Эволюция на одном примере. В `zettelkasten/AI_start.md` — точка отсчёта: установка v1 тремя шагами, последний из которых «попросить opencode установить OMO». Сегодня тот же workflow выглядит так:

- корневой `opencode.jsonc` задаёт `default_agent: "newton"` — и прямо в комментарии объясняет: механизм Selection, новые сессии стартуют с оркестратора, остальные агенты (`build`, `plan`) доступны через переключатель (Tab), а существующие сессии настройка не трогает;
- в `.opencode/agents/` — 11 агентов: оркестратор `newton` и десять исполнителей `material-*`.

`newton` — учебниковый «оркестратор-исполнители» из паттерна выше: `mode: primary`, модель glm-5.3, permissions «deny `edit`/`shell`/`subagent *`, затем allow десяти субагентам `material-*`» — сам оркестратор не редактирует файлы и не выполняет shell, вся работа делегирована. Исполнители специализированы по ролям — например, `material-researcher`: `mode: subagent`, лёгкая модель glm-5.3-flash (та самая, что разобрана в [заметке 01](../01_how-to-read-llm-architecture.md)), read-only права (deny `edit`/`shell`) — искать можно, менять нельзя:

```text
   opencode.jsonc: default_agent = "newton"
          |
          v
   newton  (primary · glm-5.3 · оркестратор)
   deny edit/shell/subagent *  ->  allow material-*
          |
          +-- material-research-lead --- исследование (сводный бриф)
          +-- material-writer --------- написание MD
          +-- material-linker --------- связывание заметок
          +-- material-link-checker --- проверка ссылок
          +-- material-reviewer ------- ревью материала
          +-- material-html-publisher - HTML (опционально)
          +-- material-toc ------------ оглавление и теги
          +-- material-cleaner -------- чистка временного
          +-- material-committer ------ коммит
          +-- material-researcher ----- read-only поиск (glm-5.3-flash)
```

От «поставь мне OMO» — к одиннадцати своим файлам с точными правами. Это и есть конец эры OMO.

## Мультиагенты одним взглядом

| Вопрос | Ответ |
|---|---|
| Что такое агент | именованный профиль: system-промпт + модель + permissions + отображение |
| Как задать | `.opencode/agents/<name>.md` или поле `agents`; вложенные пути → вложенные ID (`team/reviewer`) |
| Режимы | `primary` (дефолт для кастомных) / `subagent` / `all` |
| Кто стартует сессию | `default_agent`; если не годится — fallback: `build` → первый видимый primary |
| Кто выбирает субагентов | primary-агент по `description` — «витрине» агента (механизм Selection) |
| Встроенные | `build`, `plan`, `general`, `explore` (+ скрытые `compaction`/`title`/`summary`); `scout` в V2 нет |
| Права в паре parent/child | parent решает action `subagent`, кого запускать; ребёнок живёт по своим permissions |
| Порядок правил | глобальные до агентских, агентские уточняют; last-match-wins |
| Паттерн «оркестратор» | deny `subagent *` + allow конкретных ID — белый список исполнителей |
| OMO | в V2 не запускается (plugin API v1) и не нужен: режимы → свои агенты в `.opencode/agents/` |
